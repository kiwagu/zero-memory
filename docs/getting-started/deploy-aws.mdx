---
title: Deploy the server to AWS
description: Run the MCP server on AWS Lambda behind CloudFront with the CDK app in infra/aws, next to a Supabase project you already have.
---

The MCP server can run on AWS Lambda instead of a container host. The CDK
app in `infra/aws/` deploys it behind CloudFront, keeps MCP sessions and
rate-limit counts in DynamoDB, and watches it with CloudWatch alarms. The
server code is the same one the container runs; only the way requests reach
it differs.

```
MCP clients (OAuth)           AWS (one Region)
┌──────────────────┐  HTTPS  ┌─────────────────────────────────────────────┐
│ watcher, agents  │────────►│ CloudFront ── function URL ── Lambda        │
└──────────────────┘         │  (adds the       (refuses      (server,     │
                             │   edge header)    anything      3 GB, own   │
                             │                   else)         runtime)    │
                             │                      │                      │
                             │   DynamoDB: sessions, rate limits           │
                             │   Secrets Manager, SSM, CloudWatch          │
                             └──────────────────────┼──────────────────────┘
                                                    ▼
                                        Supabase project (HTTPS)
```

Only the MCP server moves. The dashboard, which agents need to sign in and
approve access, and this documentation site still run as described in
[Deployment](/docs/getting-started/deployment). Place the Supabase project
in the same Region as the function: every tool call makes several round
trips to it.

## Prerequisites

- An AWS account and a CLI v2 profile allowed to deploy (CDK bootstrap
  creates IAM roles).
- Docker, Bun, the AWS CLI and `jq` on the machine that deploys. The images
  are built there.
- A Supabase project with this repository's migrations applied
  (`supabase db push`), and the dashboard running somewhere reachable over
  HTTPS.

## Deploy

From `infra/aws/`, once per account and Region:

```sh
AWS_PROFILE=<profile> bunx cdk bootstrap
```

Then deploy a stage (its name is part of every resource):

```sh
AWS_PROFILE=<profile> bash scripts/deploy.sh prod -c alarmEmail=ops@example.com
```

The script builds the server image and the Lambda image on top of it,
deploys the stack, and then invokes the function once to load the embedding
model. The first read of a new image's model files can take close to a
minute; paid there, it stays off the first search.

Write the server's environment into the stack's secret from a file of
`KEY=value` lines (`SUPABASE_URL`, `SUPABASE_ANON_KEY`,
`SUPABASE_SERVICE_ROLE_KEY`, `ZM_WEB_URL`, and a model key if you use
model-backed features):

```sh
AWS_PROFILE=<profile> bun scripts/server-env.put.ts zero-memory/prod/server-env server.env
```

`ZM_WEB_URL` must be the dashboard's HTTPS address. An instance reads the
secret when it starts.

## Your own domain

By default the server answers on the CloudFront address, which the stack
prints as `PublicUrl`. To use a host name of your own, issue a certificate
for it in ACM in `us-east-1` (CloudFront takes certificates only from
there), deploy with both values, and point the name at the `EdgeDomain`
output:

```sh
AWS_PROFILE=<profile> bash scripts/deploy.sh prod \
  -c domainName=zm.example.com -c certificateArn=arn:aws:acm:us-east-1:…
```

The public URL is the OAuth issuer. Changing it later makes every connected
client authorize again, so choose the domain before clients connect.

## Check it

```sh
curl https://<PublicUrl>/healthz      # 200 and the build version
curl https://<FunctionUrl>/healthz    # 403: the function answers only CloudFront
```

Then point an MCP client or the watcher at `<PublicUrl>/mcp` and sign in.

## Operations

- **Alarms.** Five alarms notify one SNS topic: failed or timed-out
  invocations, throttling, an invocation near the 60-second timeout, an
  instance that failed to start, and repeated 5xx answers. With
  `alarmEmail`, confirm the subscription from the first mail. The dashboard
  `zero-memory-<stage>` shows the same metrics.
- **Spending.** The stack sets no spending limit; set one for the account.
- **Logs.** The function's log group keeps one week. A failed start writes
  its reason there.
- **Client addresses.** CloudFront writes the address it saw into its own
  header, and the function rate-limits on that, never on the
  `X-Forwarded-For` a client sends.

## Limits

- A request that runs longer than 60 seconds is cut by CloudFront, so the
  function's timeout is 60 seconds too.
- An instance's first search waits for the embedding model to load
  (seconds).
- The background jobs the container runs on a timer — hygiene scans, usage
  roll-ups, translation — do not run on Lambda yet.

## Remove

```sh
AWS_PROFILE=<profile> bunx cdk destroy -c stage=prod
```

This deletes the function, the tables, the secret, the parameter, the alarms
and the logs. The CDK bootstrap stack and the images it pushed stay.
